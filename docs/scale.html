05 Scale

Supercomputer-Scale Inference

Cloud-native workflows and reproducible inference on a High-Performance Computing cluster.

Introduction

AI models are growing in both size and capability, and the tasks they perform are growing in length and complexity (Frontier AI Trends Report). AISI's evaluations and experiments increasingly require self-hosted models, fine-tuning experiments, and sometimes training from scratch. At the same time, the number of researchers and experiments AISI supports is growing, and new models are released at a rapid pace set by the labs. Our research needs to keep up if it is to remain relevant.

Isambard-AI, the UK's national AI supercomputer, gives us the raw GPU capacity to keep up. But integrating a supercomputer into an existing cloud platform without disrupting researcher workflows is hard. The existing platform runs on AWS, and researchers have built workflows around EC2 instances, Docker containers, and Kubernetes. Porting those workflows to a High-Performance Computing (HPC) environment takes significant effort, and maintaining two separate ways of working creates friction that slows everything down.

In development of workflows for our Research Platform and on Isambard, we are aiming for platform consistency: Isambard should feel like a natural extension of the AISI Research Platform, with the same IDE, tooling, workflows, and security model. Knowledge about how to build, deploy, and validate workloads on HPC is captured in declarative, version-controlled configuration so that when one person solves a problem, everyone benefits.

We have built a suite of software tools to support our workflows across environments. We plan to open-source many of these tools soon.

Deep dives

AISI CLI

The existing development environments are EC2 instances. A researcher runs a single command to create a VS Code tunnel to a VM in AWS. HPC workflows are optimised for ad-hoc usage and asynchronous jobs, not persistent dev environments. Getting a comparable setup means manually installing certificates, setting up your dev tooling, and submitting SLURM jobs to create a VS Code tunnel on a compute node. That friction disrupts productivity and slows adoption.

It's also easy to make security mistakes. HPC clusters are shared, so configuring file permissions incorrectly means another user can read your data. Researchers used to isolated cloud VMs don't necessarily think about that, and worrying about it slows people down too.

The AISI CLI is a command-line tool that researchers use to manage their development environments. On AWS, it gives researchers an interactive VS Code session on an EC2 instance in a couple of commands. The isambard subcommand extends it to Isambard in an attempt to mirror the experience. It handles auth, bootstraps dev tooling, and allows users to provide custom setup scripts to configure their personal tooling in a reproducible way. Secure defaults like umask 0077 (which ensures new files are only readable by their owner) are preconfigured, so researchers don't have to think about them.

Researchers now work across AWS and Isambard as though they are part of the same platform. Environment configuration is captured in setup scripts rather than manual steps, so it's reproducible across sessions and shareable between researchers. Some power users run aisi isambard tunnel as their morning routine and develop on Isambard for the entire day.

Sifter

Unlike cloud VMs, where each researcher controls their own machine, HPC is shared infrastructure. The CUDA driver, the networking stack, and the filesystem are managed at the cluster level. Porting a workload that ran fine on EC2 demands a lot of effort to satisfy those constraints. Getting the compilation flags, CUDA compatibility layers, and networking configuration right requires expertise. Containers are a natural solution that enable packaging everything above the driver level into a reproducible image. Docker doesn't run on HPC (no root access), but Apptainer does.

We built an initial monorepo of Apptainer definitions, which helped build our workflow but had limitations. As Isambard adoption scaled and the number of workloads grew, so did the number of container variants: different inference engines, CUDA compatibility layers, and model-specific configurations. Containers also layer on each other. A base PyTorch image, an inference engine like vLLM built on top, a specific model setup on top of that. Making a change to the base image means everything downstream needs rebuilding.

Container variants multiply as CUDA versions, PyTorch versions, and inference engines combine. A change to any base image cascades downstream.

At AISI, container images are typically built and tested in CI. For Isambard, containers need to be built and tested on the cluster itself to ensure they work against its specific drivers and hardware. Configuring CI to submit and manage jobs on an HPC cluster is not straightforward, so builds were manual: figure out which images are affected by a change, work out the right build order, wait for each build to complete before starting the next. That process became tedious and broke down as the number of variants grew.

Sifter makes Apptainer builds easy and reproducible on Isambard. A sifter.yaml manifest declares every container, its dependencies, and its build parameters. When you run sifter build --all, it constructs a dependency graph, works out what's changed, and submits the affected builds to SLURM as a chain of dependent jobs. SLURM handles the parallelism and ordering.

This produces a shared library of container images that are reproducible, tested on the target hardware, and easy to maintain. Details like native Slingshot networking configuration are baked into the container builds so that researchers don't have to figure them out themselves. Porting a workload to Isambard becomes a one-time cost: one person gets it working in a container, publishes it to a remote registry, and everyone else can consume it immediately. The workflow mirrors how researchers already build and share Docker images on AWS, just adapted for HPC constraints.

Model Serving

The largest open-weight models don't fit on a single GPU and need to be distributed across multiple GPUs, often across multiple nodes. One approach at AISI is to use vLLM for serving, Ray for multi-node coordination, and SLURM for GPU allocation. Tensor parallelism splits model layers across GPUs within a node over NVLink, while pipeline parallelism distributes stages across nodes over the Slingshot interconnect. But there are many more parallelism strategies (data, expert, context) that can be combined in different ways depending on the model architecture and serving requirements, and some models need specific backends, attention kernels, or quantisation schemes on top of that. Isambard has 4 GPUs per node, which is unusual. Most of the industry assumes 8, so published deployment recipes and inference engines often don't work out of the box. Getting this right matters, because evaluations for frontier models can involve long, multi-turn interactions, and inefficient serving doesn't just waste compute, it delays results.

The vLLM Apptainer container (built and maintained via Sifter) provides the inference runtime. vllm-serve is a lightweight CLI that sits on top of it, reading declarative YAML model recipes and translating them into multi-node SLURM jobs with the right configuration. Each recipe captures the parallelism strategy, backend, quantisation scheme, and any model-specific flags needed to serve that model on Isambard's hardware. Running vllm-serve <model> looks up the recipe and handles the rest. When a new model is released, someone develops the right configuration, adds a YAML entry, and adds it to our repository of shared definitions. The recipe library currently covers 100+ models and grows with every new deployment.

yaml# Model recipes for Isambard (4x H200 GPUs per node)

model-a/Model-A-70B-Instruct:
  vllm_args:
    tensor_parallel_size: 4
    enable_auto_tool_choice: true
    tool_call_parser: model_a

model-b/Model-B-700B-Instruct:
  vllm_args:
    tensor_parallel_size: 4
    pipeline_parallel_size: 4
    enable_expert_parallel: true
    quantization: fp8
    kv_cache_dtype: fp8

model-c/Model-C-400B-MoE:
  vllm_args:
    tensor_parallel_size: 4
    pipeline_parallel_size: 2
    enable_expert_parallel: true
    max_num_batched_tokens: 8192

The effort of figuring out how to serve a model on Isambard's hardware is a one-time cost. Once someone has worked out the right configuration, every other researcher who needs that model gets it without having to understand the underlying parallelism or SLURM mechanics. For them, it's a single command: vllm-serve <model>.

Gimlet

The scale of compute on Isambard is most valuable when researchers can easily consume the workloads running on it from across the entire platform. Consider this common scenario. A team has deployed a new model on Isambard and wants researchers on AWS dev VMs to run evaluations against it using their usual tools. Or a researcher running a service on one Isambard node needs to reach it from another. HPC clusters don't accept inbound HTTP traffic, and binding a service to 0.0.0.0 on a shared cluster exposes it to hundreds of users across institutions. For sensitive work, that's not acceptable.

Gimlet solves this using a reverse HTTP tunnel. The workflow for exposing a service is: bind it to localhost, generate a token with gimlet jwt agent, and start the agent pointing at your service. The agent makes an outbound WebSocket connection to a Gimlet server running in AWS. On the consuming side, researchers generate a client token with gimlet jwt client and make standard HTTP requests to the server with it as a bearer token. The server relays requests through the tunnel to the service on Isambard. The service is never exposed to the cluster, and researchers consuming it don't need to know anything about the underlying networking.

Both sides connect to the Gimlet server. The tunnel initiates outbound from Isambard, so no inbound firewall rules are needed.

Tokens are JWTs signed by AWS KMS keys that live within specific project namespaces, the same boundaries that govern everything else in the platform. If a researcher has access to a project in AWS, they can expose and consume services on Isambard through Gimlet without separate credentials or access requests. Tokens are scoped to specific services and have short lifetimes, typically 24 hours. From a researcher's perspective, accessing a service on Isambard feels no different to accessing one on AWS.

MBench

A model that starts and responds to requests isn't necessarily working correctly. The networking stack might have silently fallen back to TCP, tool calls might be broken, or performance might degrade under concurrent load. Discovering these issues mid-evaluation means wasted compute and potentially having to start from scratch. Without a consistent validation process, these checks are ad-hoc and the same problems get rediscovered by different people.

MBench applies the same pattern as the rest of the tooling: capture validation in declarative config files so it's reproducible and shareable. A single config file declares the endpoint, dataset, load parameters, and the checks to run. One command exercises the deployment across functional tests (are responses well-formed, do tool calls work) and load tests (throughput and latency at increasing concurrency). It integrates natively with Gimlet, handling JWT auth automatically when pointed at a Gimlet URL.

json{
  "name": "model-a-validation",
  "base_url": "https://gimlet.apps.aisi.org.uk/services/model-a/v1",
  "api_key": {
    "gimlet": {
      "kms_key_arn": "arn:aws:kms:..."
    }
  },
  "model": "model-a",
  "endpoint": "/chat/completions",
  "parallelism": [1, 2, 4, 8, 16],
  "duration_s": 300,
  "stream": true,
  "max_completion_tokens": 200,
  "dataset": {
    "name": "HuggingFaceH4/ultrachat_200k",
    "split": "train_sft",
    "prompt_field": "prompt"
  }
}

Validation becomes a versioned, repeatable step, rather than a manual process. The same config file can run against every new deployment, whether on Isambard or AWS, so regressions are caught early and nobody wastes time rediscovering known issues.
