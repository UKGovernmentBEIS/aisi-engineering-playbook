03 Connect

Multi-Provider Model Access

A transparent proxy that routes every model call through one audited layer.

What is a model access layer?

Researchers call models from multiple providers, and as an organisation grows it needs to know what was sent where, control the costs, and revoke access instantly. Any control that adds friction that slows down research is liable to be routed around, and a layer researchers bypass records nothing.

A transparent proxy can solve for this. A researcher switching from direct API access to the proxy changes a couple of environment variables. The proxy handles authentication via temporary credentials, logs every request and response, provides per-team token usage, and supports instant revocation without touching researcher machines.

A model access layer sits between researchers and the model providers they call. It handles authentication, routes traffic to the right upstream, logs interactions, and enforces organisational policy.

There are two obvious ways to build this. The first hands each researcher a provider API key directly. The second wraps every provider SDK in an internal library that researchers import instead of the real one. Both work effectively with a handful of researchers but then strain as the numbers grow.

ApproachWhere it strains
Hand each researcher a provider API keyCost attribution is only via the providers' dashboards and doesn't include internal org structure. Preventing leaks requires every researcher to secure their machines individually.
Wrap every provider SDK in an internal libraryWrappers are often brittle and lag new provider features. Researchers reach for whatever tool fits the task and route around the library when it gets in the way. If the raw key ever passes through a researcher machine, it's exposed to leaks.

A transparent reverse proxy avoids both sets of problems. SDKs point at it via one or two environment variables and application code does not change.

Challenges to solve for

Invisible adoption

Any layer that asks researchers to install a library, import a wrapper, or change an SDK invocation can add friction and frustration.

Credential rotation

Provider API keys are long-lived and unscoped. Distributing them removes the ability to attribute usage to an individual, expire credentials automatically, scope access to a specific project, or revoke one user without rotating the key for everyone.

Logging all traffic

Retaining logs of all requests and responses allows for analysis of API usage (including model token usage) and post-hoc investigation.

AISI's implementation

AISI's API key proxy is called Portunus, and provides transparent proxying to any API, credential handling using AWS IAM and AWS Secrets Manager, and audit logging of all requests and responses. We aim to open-source Portunus soon.

Portunus has run in production since our earliest technical work. In the current generation, Envoy reverse-proxies in front of a backend service that handles credential exchange and audit publishing. About 150 researchers across 20+ teams send traffic to Portunus daily, calling roughly a dozen different API providers.

Each provider gets a dedicated subdomain, such as openai.proxy.aisi.gov.uk or anthropic.proxy.aisi.gov.uk. We deploy all our infrastructure with AWS CDK, and adding a new direct provider involves a CDK stack update pointing at the upstream target. Adding a model available through OpenRouter or Bedrock is just a secret update.

Researcher dev VMs are pre-configured at boot, where cloud-init writes relevant environment variables to /etc/environment so SDKs read them automatically.

The following sections detail the design and implementation of Portunus.

The transparent proxy pattern

Every major model SDK reads its endpoint from an environment variable: OPENAI_BASE_URL, ANTHROPIC_BASE_URL, MISTRAL_API_BASE. Pointing those at a reverse proxy and replacing the API key with a short-lived credential routes every request through the access layer without any change to application code. The migration cost for setup is two environment variables, in any language, with any HTTP client.

A request reaches the proxy carrying a credential that isn't a provider key. The proxy resolves it to a real API key from secrets storage, swaps the auth header, forwards the request upstream, and logs both halves on the way back.

The credential

In AISI's Research Platform, the typical environment variables are overridden with an AWS ARN-shaped URI naming a secret in AWS Secrets Manager:

bashOPENAI_API_KEY=aws-secretsmanager://arn:aws:secretsmanager:eu-west-2:...:secret:teams/aisi/openai-api-key-xxxxx

Before each request leaves the machine, the URI is rewritten into a base64-encoded payload of temporary AWS credentials. The credentials come from sts:AssumeRole with a session policy scoped to one ARN, capped at the STS maximum of 12 hours. For evaluations that run through Inspect, an override_api_key hook does the rewrite at model init. For use in other tools, we've written a small command-line tool that handles this credential encoding.

The payload looks like an opaque token to the relevant SDK, which will set it as the relevant authorization header (e.g. Authorization: Bearer). The proxy decodes it, fetches the real key from Secrets Manager using the embedded credentials, and substitutes the header before forwarding. The temporary credentials are usable only against that one Secrets Manager ARN, and only from one place.

Where the secret can be read

Reading a real provider API key requires two capabilities: IAM scope and network origin.

Researcher IAM identities are granted secretsmanager:GetSecretValue on path-scoped ARNs: users/{name}/*, teams/{slug}/*, projects/{slug}/*. A researcher can name secrets that belong to their own identity and group memberships but not name secrets belonging to another team.

API key secrets carry a resource-based deny policy that rejects GetSecretValue from any source except the VPC endpoints belonging to the proxy. A researcher with administrative AWS credentials, sitting on their dev VM, and attempting to read their own team's OpenAI key directly, gets AccessDenied. The proxy reads the same secret from inside its VPC using credentials minted from a researcher's session and succeeds.

For a real key to reach a researcher, both gates must fail at once and these sit with different parties. The researchers hold the IAM scope, while the network origin belongs to the proxy, which runs in infrastructure a separate platform team operates. This construction is the standard AWS data-perimeter pattern. What's uncommon is applying it to third-party API keys behind a transparent proxy that researchers don't opt into.

The dual gate. Reading a key needs both an identity capability (which secrets you may name) and a network capability (where the read may originate). The two sit with different parties, so a researcher with full IAM access still can't read the raw key from their own machine, only the proxy, from inside its VPC, satisfies both.

Audit logging

Routing every model call through Portunus means AISI retains the corpus of its own traffic. Many major LLM providers offer Zero Data Retention agreements, meaning they do not retain prompts or completions from user traffic. AISI has found it valuable to retain our own copy of LLM logs (including prompts and responses) for analysing usage and investigation.

Through log analysis, our LLM provider usage is attributable to project, team, researcher, and model. A token-usage dashboard reads from the archive and surfaces team-level breakdowns and SQL queries. Sensitive projects get model and provider names hashed before the data lands in the dashboard, so cross-team visibility doesn't leak evaluation details.

The corpus. Because every call routes through the proxy and providers operate under Zero Data Retention, the record lives org-side. The captured stream feeds audit and cost attribution.

What transfers

We hope some of Portunus' design can be helpful to other organisations. For example, setting OPENAI_BASE_URL and OPENAI_API_KEY (and the equivalents for other providers) to point at a reverse proxy routes traffic through the layer without any code change. The proxy can be anything that intercepts and rewrites the Authorization header.

Another transferable part of the design is the use of Secrets Manager URIs. An ARN-shaped URI goes in the API key field and is rewritten into short-lived credentials by the SDK or a small helper before each request. The real provider key never lands on the researcher's machine, only a short-lived credential that expires and works through the proxy alone.

A third part is the dual gate, where an identity capability names what can be read and a network capability determines where it can be read from. A key is only accessible when both line up. Many internal LLM gateways work only on the identity half.

The implementation choices here are infrastructure reference examples rather than requirements. Secrets Manager, STS, Kinesis, and VPC endpoints have direct equivalents in other clouds. Envoy is convenient because its filter chain makes the credential swap clean, but Nginx, HAProxy, or a custom reverse proxy work too. Inspect's override_api_key hook is how external collaborators integrate the credential exchange invisibly, and any framework with equivalent extension points works the same way.
