04 Run

The Research Platform

The platform researchers work from, with their tools, data, and compute already in place.

Developer platform vs research platform

A developer platform helps you write and ship code. You could do that on your own machine, or with an off-the-shelf product like GitHub Codespaces. Either way, little has to be built. The hard parts are a runtime, an editor, version control, and a way to deploy, and those are much the same wherever you work. To run a research workflow end to end, a research platform has to do much more.

The valuable, sensitive material is the research data, the model weights, and access to specialised compute like GPUs. None of this belongs on a laptop, and it cannot be served by an off-the-shelf coding environment. So on top of the developer platform basics, a research platform manages research data, controls who can reach which project's data and models, and gives researchers GPUs and other large-scale compute.

Depending on the nature of the research, a single piece of work might involve running evaluations against a frontier model, fine-tuning a model and then evaluating the fine-tuned version, pulling a few thousand evaluation logs out of storage to derive metrics, or building a small web application the rest of the team can open in a browser. These happen in different orders and combinations, and the same researcher will do several of them in a week.

This section walks through the infrastructure AISI has built for that, and the design choices behind it. The thread running through all of it is what a small platform team can sustainably own. Not building each researcher's environment by hand, and not operating every application on their behalf, but shipping a set of composable building blocks that researchers can assemble themselves.

Constraints and challenges

The managed laptop

At AISI, a researcher's starting point is their government-issued laptop, which is centrally managed. That gives you a known security baseline and central monitoring out of the box. The cost of this is researchers not having admin access, and only installing software from a short allowlist. Turning each laptop into a real development machine through exceptions would be slow and leave a fleet of subtly different machines, so the workable answer is to develop code somewhere other than the laptop.

Research data and access control

Research runs on data that cannot sit on a laptop: a large corpus of evaluation logs, datasets, and model weights, often shared across a team. That data also carries boundaries. Some is sensitive, whilst some might belong to one project and not another. A researcher should reach exactly what their work needs and nothing more. The platform has to hold this material centrally, make it fast to reach from wherever research runs, and enforce who can see which project's data and models, without the researcher handling credentials or copying sensitive files by hand.

Specialised compute

If a researcher is fine-tuning a model, hosting an open-weights model for inference, or running a GPU-bound workload, this work will need hardware a managed laptop won't have. A researcher who needs a GPU machine should get one through the same path and the same identity they use for an ordinary development machine, without a separate request process for each kind of compute. If you now scale this up to a supercomputer-size cluster then inference is a harder problem to solve (see Scale). In either case, what matters here is that everyday access to GPU resources is part of the platform.

Deployment

Throughout the research lifecycle a tool or application is often needed to progress work. This could be an app for running a human-subject study, an internal tool that makes a workflow faster, or a dashboard that shares findings with the team. In every case the researcher has working code and needs it running somewhere the team can reach, and keep reaching, well after the experiment is done. To start with it needs a name in the domain name system and an encrypted connection, so that's a certificate. Then it needs somewhere to run, with a load balancer routing to it and health checks so a failed instance gets replaced. And it usually needs a database in a private network, backed up and reachable only by the application, whilst logs, metrics, and a way to ship a new version without downtime must all be there too. None of this stack is research, but all of it must be designed and built before anyone else can open the application.

What a small platform team can own

At AISI's size, the constraints above can be met in two ways that both break down. If each researcher solves for every constraint from scratch, then every application becomes hundreds of lines of fiddly infrastructure code. This code is easy to get subtly wrong, in ways that only surface as incidents, and any improvement made in one application stays trapped there. If instead a small platform team builds and operates everything on researchers' behalf, that team becomes the bottleneck for every piece of research that touches infrastructure, and the cost grows with every new application. The approach that holds is for the platform team to build and own a small, opinionated set of reusable building blocks, and for researchers to compose those blocks into their own applications.

The architecture

These building blocks get a researcher onto a capable machine with their tools and data already in place, and then deploy what they build on it. Three of the building blocks handle the machine and its data, and the fourth handles deployment. A researcher logs in, lands on a ready machine, reaches the data and compute their project allows, and composes a short stack file to deploy what they have built.

The researcher's path end to end. Federated login mints short-lived credentials, the CLI provisions a machine (development or GPU) from the golden AMI, that machine reaches only its project's data under a scoped identity, and a short stack file deploys the application.

Getting onto compute

The starting point is a command-line tool on the managed laptop. The researcher logs in against the organisation's identity provider, completes a multi-factor challenge, and the tool exchanges the result for short-lived cloud credentials that expire in hours. Every later command uses those credentials, so there is no long-lived cloud key on the laptop. The same tool owns the lifecycle of the machine the researcher actually works on. One command provisions a development machine, and another opens a tunnel so the local editor attaches to the remote filesystem and terminal as if the project were local. A GPU machine comes through the same command on the same identity, so specialised compute is a parameter rather than a separate request.

That tool runs against a near-bare standard-library Python interpreter, with no third-party runtime dependencies, because adding packages to a managed laptop is slow or unpredictable. The laptop side is then a thin client, and a backend with full access to the cloud software development kit does the real work. Features ship on the backend without anyone updating local tooling, a bad release is reverted server-side, and the review surface for each change stays small. The cost is that the tool does little on its own and assumes the backend is reachable, which is the right trade for a fleet of locked-down laptops. The pattern of trading a long-lived key for a federated login and short-lived credentials is portable, while the specific identity provider and cloud are AISI's.

The golden AMI

A machine is only useful once the researcher's tools are on it, and installing them by hand turns every new machine into more than a day's worth of setup. Instead every development machine boots from one maintained image, the golden AMI (Amazon Machine Image), carrying the standard developer runtime, cloud tooling already pointed at the team and project resources the researcher can reach, AI coding assistants, and the platform's security baseline. The researcher opens a terminal and the environment is ready, and crucially the same on every machine.

The harder part of that image is credentials. AI coding assistants need a model key to work, and the researcher doesn't hold the key. A small helper on the machine fetches a short-lived key from a central store at runtime, and the assistant is configured so that environment variables cannot be used to bypass the helper. Rotation and revocation happen centrally, and the researcher's setup does not change when either does. This is the part of the platform closest to something a reader could assemble from existing products, since a maintained image and a managed development machine are well-trodden ground. What the image gives up is bespoke setup, since a researcher is on the platform's image and its version rather than a machine tuned to their taste. Whilst some will miss this, the payoff is that every machine gets the next security fix the moment the image rolls forward.

Data and access-control model

A ready machine has to reach the right data, and only the right data. The platform runs each machine under the researcher's federated identity, so the cloud tooling on it can reach the team and project storage that identity is allowed to reach and nothing else, with no access keys on disk and no files copied down by hand. Access is scoped by project and team, so a researcher reaches what their work needs while sensitive material stays bounded to the people who should see it.

The mechanics of how those boundaries are drawn and enforced are deliberately out of scope for a public page. What transfers is the principle of running researcher workloads under a federated identity scoped to a project, so that access follows from who someone is rather than from the credentials they carry.

The construct library

A finished web application, whether it runs a study, supports a workflow, or shares findings, still needs everything in the deployment constraint before anyone else can open it. We developed a construct library for AWS CDK (Cloud Development Kit) - an internal Python package that turns that long list of requirements into a few opinionated building blocks: a containerised web application reachable at a subdomain, a database carved from a shared cluster or a dedicated instance, a managed cache, and a scoped role for deployment. Each block is a single class with a typed interface, and from it the library produces the load-balancer rules, the task definitions, the network configuration, the identity and access management, the domain name, and the certificate, with the platform's defaults already applied.

A researcher's whole application is then a short composition of those blocks:

pythonclass StudyAppStack(Stack):
    def __init__(self, ...):
        super().__init__(...)

        # A dedicated database for study responses.
        db = DedicatedDatabase(self, "Database", name="study_responses")

        # The app, reachable at study.<platform-domain>.
        ContainerisedWebApp(
            self, "StudyApp",
            subdomain="study",
            containers=[Container.from_asset("./app", port=8080)],
            environment={"DATABASE_HOST": db.endpoint},
            secrets={"DATABASE_PASSWORD": db.password_secret},
        )

This is around thirty lines, most of which is configuration for the application container. The researcher writes no networking, load-balancer rules, container orchestration, identity and access management, or domain configuration, and the deployment itself runs on short-lived federated credentials rather than a static key stored in the repository. The library matters because it consolidates the work so that a security improvement to how deploy roles are scoped is one change against the library rather than a migration across every application repository. Opinions about log retention, rollback, and permissions then accumulate in one place. The trade-off is that a researcher on the library is constrained to the shapes it supports. An application that needs something unusual, such as a protocol the shared load balancer does not route, or a region outside the platform's footprint, has to extend the library or step outside it. In these more unusual cases the platform team gets involved directly.

The broader picture

This layer is central as the platform is where all the other layers are used from. Model access on a development machine works through the proxy pattern described in Connect. Doing inference at supercomputer-scale, the harder version of the specialised-compute constraint, has its own answer in Scale. The evaluations a researcher runs from a platform machine provision the sandboxes described in Evaluate and Isolate, and the platform is where that run is launched, watched, and its logs collected.

Run is the hub the other layers are used from. Model access (Connect), large-scale inference (Scale), and launching evaluations with their sandboxes (Evaluate and Isolate) are all reached from a platform machine.

What transfers

Unlike the other sections in this playbook, you'll notice this section does not contain open-source tools that you can install and use. AISI's Research Platform is internal to AISI and built on AWS and UK government IT, so the value of this section is in the patterns, rather than the code. The specific cloud, identity provider, and hardware are AISI-specific, but federating login to short-lived credentials, maintaining a single machine image (with credentials fetched at runtime), and maintaining a small composable infrastructure library, are useful patterns for other organisations.
